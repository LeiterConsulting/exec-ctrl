# Exec-Ctrl Method-Repo Refinement Scorecards

## Purpose

Use these scorecards when a refinement inside a method, prompt, template, or governance repository feels larger than one tiny slice but smaller than a true whole-system redesign.

They calibrate the use of [EXEC_CTRL_BOUNDED_VS_WHOLE_SYSTEM_SCORING_RUBRIC.md](EXEC_CTRL_BOUNDED_VS_WHOLE_SYSTEM_SCORING_RUBRIC.md) for self-hosting work.

## Scorecard 1. Prompt Family Hardening

Request shape:

`Tighten the method-evolution and checklist-review prompts so they route to the right docs and use the same scope language as the self-hosting guide.`

| Category | Score | Why |
| --- | --- | --- |
| Surface breadth | `0` | one adjacent prompt family is changing |
| Authority impact | `0` | the authority model stays intact |
| Dependency spread | `1` | the prompts and one guide need coordinated updates |
| Validation breadth | `0` | a narrow coherence pass is enough |
| Reuse scope | `1` | the change improves a recurring but bounded workflow |
| User wording | `0` | the request names one bounded family of surfaces |

Total:

- `2`

Recommended path:

- initiative mode

## Scorecard 2. Cross-Surface Self-Hosting Alignment

Request shape:

`Align the README, self-hosting guide, workspace guidance, prompt pack, and planning surface around a tighter method-evolution intake flow without changing the underlying authority model.`

| Category | Score | Why |
| --- | --- | --- |
| Surface breadth | `1` | several adjacent surfaces change together |
| Authority impact | `1` | the work clarifies how one bounded intake pattern should operate |
| Dependency spread | `1` | docs, prompts, and planning all need coordinated updates |
| Validation breadth | `1` | multiple adjacent surfaces need coherence validation together |
| Reuse scope | `2` | the outcome influences several self-hosting workflows |
| User wording | `1` | the wording is broad but still plausibly bounded |

Total:

- `7`

Recommended path:

- initiative mode with explicit boundaries, non-goals, and watchpoints

Suggested watchpoints:

- do not change the status vocabulary or phase model in the same slice
- keep the new intake flow subordinate to the existing authority order

## Scorecard 3. Example-Library Expansion

Request shape:

`Add new generic example packs for prompt-library evolution, template hardening, and governance-model migration so self-hosting has better pattern coverage.`

| Category | Score | Why |
| --- | --- | --- |
| Surface breadth | `1` | multiple example surfaces change, but the rest of the method remains stable |
| Authority impact | `0` | examples do not redefine the core method |
| Dependency spread | `1` | examples and a few routing docs need alignment |
| Validation breadth | `1` | the claim needs an example-focused coherence pass |
| Reuse scope | `1` | the outcome improves several recurring but still bounded teaching surfaces |
| User wording | `0` | the work is clearly framed as one bounded expansion |

Total:

- `4`

Recommended path:

- initiative mode

## Scorecard 4. True Whole-System Redesign

Request shape:

`Redesign the repo so the numbering model, authority order, phase advancement rule, and baseline status vocabulary all change for future work.`

| Category | Score | Why |
| --- | --- | --- |
| Surface breadth | `2` | many core surfaces change together |
| Authority impact | `2` | the control model itself is being replaced |
| Dependency spread | `2` | the change cascades across most guidance surfaces |
| Validation breadth | `2` | broad repo-wide validation is required |
| Reuse scope | `2` | the outcome becomes baseline guidance for most future work |
| User wording | `2` | the user explicitly asks for repo-wide redesign |

Total:

- `12`

Recommended path:

- whole-system control path

## Practical Rule

If a self-hosting request changes several adjacent docs, prompts, templates, and examples but leaves the core authority model intact, it usually still belongs in initiative mode.

Escalate only when the refinement replaces the baseline execution model for most future work.
