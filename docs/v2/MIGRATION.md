# Migrating from v1

Use [START_HERE.md](../../START_HERE.md) for new work. Existing v1 projects do not
need to rename their six-file project pack or three-file initiative pack.

1. Preserve current status, decisions, evidence and unfinished gates. Identify
   which v1 records remain active; historical completion claims stay historical.
2. Add a versioned adoption note to existing guidance when persistent adoption is
   authorized. Record the source revision and local adaptations.
3. Use v2's authority boundary: host and applicable policy first; status is a claim
   checked against evidence. Do not elevate old document ordering over actual rules.
4. Select relevant modules from the task and risk. Map new obligations into existing
   records instead of creating a parallel control system.
5. Collapse redundant future recordkeeping where useful. Existing documents can
   remain; v2 removes mandatory document counts, not valuable history.
6. Check adapters and prompts for conflicting defaults. Thin native pointers can
   coexist. Never overwrite unrelated target instructions while upgrading.
7. Revalidate changed behavior and resume unresolved work. Migration itself does
   not turn pending or deferred gates into passes.

The preserved [v1 guide](../../V1_README.md), legacy manuals, template packs and
examples are labeled reference material. Old saved prompts must explicitly select
v1 to use its workflow; otherwise follow v2 and retain only relevant task intent.

## Between v2 previews

Pin the helper used to validate historical records. Machine records declare an
exact framework version; a preview.1 record is not silently accepted by preview.2.
For ongoing work, review the new controls, create an updated record with the current
version, reroute its facts/policies and revalidate the evidence. Keep the original
record and evidence intact. Preview.2 makes policy-file ordering irrelevant without
weakening content hashes or allowing recorded policies to be omitted.
